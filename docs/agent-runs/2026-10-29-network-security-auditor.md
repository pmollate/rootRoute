# network-security-auditor · live Azure + HTTP surface after sign-in setup · 2026-10-29

**Asked by:** Priyank (via the main session) · **Branch / commit:** `agents-security-privacy` @ `79df1b6` (live API reports `GIT_SHA` 14411e6)
**Request:** Read-only audit of the live Azure setup, the app's HTTP surface, secrets and dependencies after today's
sign-in configuration (Auth.js demo accounts live, `AUTH_REQUIRED` deliberately still off), against SPEC §8 (SEC-*) and
SPEC-auth §4.2, §6, §10.

**Verdict:** Transport, browser secrets and MCP are sound, but with `AUTH_REQUIRED` off anyone on the internet can
drive every agent gate (approve, WMS entry, client replies, Gmail fetch, LLM calls) anonymously through the web proxy,
and two LLM/write routes need no credential even on the API directly. Switch `AUTH_REQUIRED=on` before the site is
shown to anyone outside the team.

## Switching `AUTH_REQUIRED` on (what is in place, what is missing)

- In place on `rootroute01-web`: `AUTH_URL`, `AUTH_TRUST_HOST`, `API_URL` (server only), `AUTH_DEMO=on`. Key Vault
  references for `AUTH_SECRET`, `INTERNAL_AUTH_SECRET`, `AUTH_DEMO_USERS` and `API_KEY`.
- In place on `rootroute01-api`: a Key Vault reference for `INTERNAL_AUTH_SECRET` (the API refuses to start under `on`
  if it is under 32 bytes: SEC-AUTH-09, T11).
- Missing: `AUTH_REQUIRED` is not set on either app, so it defaults to `off`. Entra is not configured
  (`AUTH_MICROSOFT_ENTRA_ID_*` are absent; `/api/auth/providers` lists only `demo`), so after the switch only demo
  accounts can sign in.
- To switch: run `az webapp config appsettings set -g rg-unhandled-rejections -n rootroute01-api --settings AUTH_REQUIRED=on -o none`,
  then the same for `rootroute01-web`. Each app restarts. Then check: `/dashboard` redirects (307) to `/login`; anonymous
  `GET https://rootroute01-api…/api/overview` returns 401; the API sends no `Access-Control-Allow-Origin`. The CD `e2e` job
  needs `E2E_DEMO_PASSWORD`, and the smoke step's `curl -L $WEB_URL/dashboard` will land on `/login`. Confirm it still
  passes. To roll back, set `AUTH_REQUIRED=off` on both apps.

## Checked and found fine

- Transport: both apps `httpsOnly=true`; `http://` returns 301 to `https://`; min TLS 1.2 on app and SCM; remote debugging off; client certs off.
- SCM/Kudu and FTP basic publishing credentials are disabled on both apps (`basicPublishingCredentialsPolicies` ftp/scm `allow=False`); SCM returns 401 to basic auth.
- Postgres: `require_secure_transport=on`, `ssl_min_protocol_version=TLSv1.2`, `log_connections=on`, PG 16.
- Key Vault: soft delete on (90 days); 8 secrets, all enabled. The only human principal is one team member (secrets get/set/list).
- Secrets in code: `git grep` over tracked files and `git log --all -p` over history found 0 hits for OpenAI/AWS/Google/GitHub/Slack key shapes, PEM private keys, `API_KEY=<32-hex>`, `MCP_TOKEN=<48-hex>` or Postgres URLs with a password. `.env` is gitignored and not tracked. CD uses OIDC (`id-token: write`, no stored Azure password) and masks Key Vault values.
- `NEXT_PUBLIC_` in frontend source: only in the server-side proxy route (`route.ts`), never in browser code.
- Proxy: GET and POST only; fixed `API_URL`; returns only body and content type (no API headers or cookies reach the browser).
- MCP: 401 without a token or with a wrong one; 503 when unset (in code); tools are read-only (REQ-MCP-01).
- Outbound email: `sendReply` (`backend/api/src/modules/intake/mailbox.ts:102`) refuses any address not on `ALLOW_LIST` before calling Gmail. `ALLOW_LIST` on the API holds 1 address (SEC-03). External hosts called: `oauth2.googleapis.com`, `gmail.googleapis.com`, `atlas.microsoft.com`, the Azure OpenAI and Azure Language endpoints.
- `backend/api` `npm audit --omit=dev`: 0 vulnerabilities. Next.js 15.5.28 is past the middleware-bypass fix (CVE-2025-29927).
